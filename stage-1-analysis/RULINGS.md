# Stage 1 — Rulings (Analyst)

Ambiguities found in `stage-1.md` and the reading the band adopts. Each ruling picks the reading
most consistent with the rest of the specification. "Tested" names the acceptance test that pins
the ruling; "untested" rows are guidance for the implementer and reviewer only.

| ID | Question | Ruling | Why | Tested |
|---|---|---|---|---|
| RUL-01 | Where does the analysis live? | `stage-1-analysis/` (LEDGER, RULINGS, `acceptance/`), per the coordinator's handoff, not `requirements/` inside the stage folder. | Handoff instruction. | — |
| RUL-02 | An excerpt may be any substring of prose. Truncating a sentence can manufacture a different value (`…headquartered in San` → `San`). Which value is expected? | The band cites **whole sentences** (A.1 sentences of one prose line, whitespace may be collapsed) and takes the value that sentence supports. Acceptance tests expect the whole-sentence value. Every corpus case expected to be `unknown` is verified to have *no* supporting substring at all (`check_corpus.py`), so `unknown` expectations hold under either reading. | §4 "A string value is written as the supporting excerpt writes it"; the whole-sentence value is the only one stable under every excerpt choice and is what A.2's examples show. | `test_R_EVD_08_*` |
| RUL-03 | Can a supporting sentence span a line break (an excerpt may collapse `\n` to a space)? | No. A.1 splits prose into lines first; the service cites only excerpts within one line. The analyst corpus contains no cross-line statements. | A.1 first sentence. | untested (avoided) |
| RUL-04 | Is the support rule applied to the excerpt as written or whitespace-collapsed? | Collapsed (every whitespace run → one space), then trimmed. | A.1 "with every run of whitespace written as one space"; §4 citation rule. | oracle |
| RUL-05 | An amount that is not a whole number of dollars (`$12.5`). | It is still an amount (its number is not a headcount/founded number), but it is not a value, so an excerpt containing it supports no `funding_total`. | A.5 "is not a value"; rule 5 "every value in F's format … normalises to V". | oracle unit only |
| RUL-06 | `founded_year` "a number of exactly four digits": does `Acme Robotics was founded in 2,014.` contain a value (Reviewer question)? | **No value.** "Exactly four digits" is about the number as written: `2,014` is a number (A.4 allows group commas) but it is written with a `,`, so it is not a four-digit number; `2014.0` likewise (decimal part). Such a sentence supports no `founded_year`. (`2,014` is still a number for `headcount_range`.) | A.4 "A number of exactly four digits, from 1800 to 2099": the format describes how the year is written, and a year is never written with a group comma; reading it as the numeric value would make "four digits" redundant with "1800 to 2099". Implementation and oracle already agree. | `test_oracle_unit.py` (`founded in 2,014`, `founded in 2014.0`) |
| RUL-07 | What is a header line? | First line of the served text matches `^[A-Z][a-z]+(-[A-Z][a-z]+)*: `; then every line up to the first empty line is header. Otherwise there is no header. | §4 Pages. | `test_R_EVD_03_*` |
| RUL-08 | Which pages are "evidence" in tests? | In the analyst corpus no page names another company, and every page of a company is returned by some query naming it (fenwick-orchards has 12 pages; its 2 fact pages are outside the domain query's top 10 but are top results for e.g. `Fenwick Orchards CEO`), so the evidence is exactly: every searchable page of the company (full text) + every Nimble research claim whose excerpt supports its value. | §4 Evidence; mock README: a domain query ranks the company's pages first, ≤ 10 results. | `check_corpus.py` |
| RUL-09 | A research claim citing a non-searchable page. | Asserted (field `known`, citation = research URL + excerpt, provider `nimble`) when the excerpt supports the claimed value; ignored otherwise. | §4 "The claim is asserted only when its citation supports it." | `test_R_EVD_06_*`, orrin-bay |
| RUL-10 | Is a snippet enough? | No. Evidence is each page's **full** text; a build must obtain full text (extract or deep search) for its evidence pages. Supporting sentences may sit beyond the first 1,500 characters. | §4 "with its full text". | `test_R_EVD_09_*`, talloway/sablewood |
| RUL-11 | Do bearer tokens issued before a reset survive it? | No. Reset replaces *all* state, sessions included. | §3.3 "Replace all service state with the fixture". | `test_R_RST_10_*` |
| RUL-12 | Fixture `users` absent. | Treated as `[]`. Not tested. | Only `now` is stated as required. | untested |
| RUL-13 | Clock edge cases. | Equal instant → 204 (only *earlier* is rejected). `Z` is an explicit offset (RFC 3339). `now` missing / no offset / unparseable string → 422 `validation_failed`; `now` of the wrong JSON type → 400 `malformed_request`. | §3.4, §5. | `test_R_CLK_05/08/09_*` |
| RUL-14 | Reset with a bad fixture. | `now` missing or invalid → 422; unparseable body → 400; nothing changes. | §3.3/§3.4/§5. | `test_R_RST_09/11_*` |
| RUL-15 | `POST /dossiers` body that is JSON but not an object (`[]`, `"x"`, `null`), or `{"domain": null}`. | Non-object body → 400 `malformed_request`. `domain: null` → either 400 or 422 is accepted. | §5 "Unparseable body, or a field of the wrong JSON type". | `test_R_ERR_02_*` |
| RUL-16 | Claimed key + body with a wrong-typed field (`{"domain": 5}`). | 409 `idempotency_key_reuse`: type checking is field validation, which comes after key resolution. An unparseable body is still 400. | §7 last paragraph. | `test_R_IDEM_12_*` |
| RUL-17 | Refresh with an unparseable or non-object body. | Ignored entirely; never a 400 for the body; replay decided by user + path + key only. | §7 "any body sent to it is ignored". | `test_R_IDEM_09_*` |
| RUL-18 | Invalid domain in a path. | 422 `validation_failed` for GET and refresh (normalisation precedes lookup), not 404. | §4 "Every domain the API takes, in a body or a path… Anything else … is 422". | `test_R_DOM_02_invalid_domain_in_path` |
| RUL-19 | Integer query parameters. | Plain ASCII digits only; leading zeros allowed (`007` = 7); empty value → 422. | §5. | `test_R_ERR_06_*` |
| RUL-20 | Same key, body domain differing only in case. | Different body → 409 on the same path. Path differing only in case → different request → normal response. | §7 "different requests for this rule". | `test_R_IDEM_06_*` |
| RUL-21 | Which body fields count for "same body"? | Only fields the endpoint defines (`domain`); unknown fields are dropped before comparison. | §7. | `test_R_IDEM_08_*` |
| RUL-22 | Export taken during a build — `spent_units`, and a build still running at import. | `state`/`fields`/`researched_at` as before the build (tested). `spent_units` not asserted. | RUL-23 | Invalid import. | Missing `track`/`format_version`/`state`, wrong track, version ≠ 1, `state` not an object or not a state this service produced → 422; unparseable → 400; destination unchanged. | §10. | `test_R_EXP_07_*` |
| RUL-24 | `spent_units` of a failed build. | Counts every unit the mock charged (e.g. timed-out calls); refused (500/429) calls cost 0, so an all-refused build adds 0. | §9. | `test_R_BLD_02_*`, `test_R_COST_06_*` |
| RUL-25 | A build whose searches succeed but find nothing. | `ready` with every field `unknown` (calls succeeded). | §8 "failed when none of its provider calls succeeded". | `test_R_SUP_12_*` |
| RUL-26 | `POST /dossiers` on a dossier that is building. | 200 with `state: "building"`; no new build. | §8. | `test_R_REF_02_*` |
| RUL-27 | Refresh of a `failed` dossier. | Allowed; starts a build. | §8 refresh "Starts a new build". | `test_R_BLD_02_*` |
| RUL-28 | Retries and the one-domain-query rule. | Refused calls (500/429) do not count. A build has **at most one** successful search whose query is the bare normalised domain. A `ready` build has exactly one, unless every attempt at the domain query was refused for the whole build (Reviewer's reading, adopted); then zero is acceptable. A build that ends `failed` has none. Where a retry can succeed within the time and budget (single 429/throttle), the tests still expect exactly one. | §4 "Of the searches that a provider answers without an error, every build makes exactly one…"; "A search that a provider answers with an error does not count." A build cannot make an error-free search the providers never allow. | `test_R_DEL_03_*`, weather (relaxed), `test_R_EVD_11_*` |
| RUL-29 | `hq_city` when the phrase is written capitalised (`Based In Lisbon`). | No value (the run starting after the phrase is part of a longer run). | A.4 "not part of a longer such run". | oracle only |
| RUL-30 | Non-ASCII capitalised words. | Unicode upper/lower case properties (`Tromsø`, `Zürich`). | A.4 "letters may be of any alphabet". | orrin-bay, wrenfield |
| RUL-31 | Email format. | Exactly one `@` with non-empty local and domain parts; tests only use clearly invalid forms. Case-folding of emails is not specified and not tested. | §6. | `test_R_AUTH_05_*` |
| RUL-32 | Legal name starting at the domain. | Counts (`acme-robotics.test Ltd`): "The company's name or its domain". | A.4. | oracle |
| RUL-33 | Missing auth fields vs wrong types. | Missing → 422; wrong JSON type → 400. | §5. | `test_R_AUTH_13_*`, `test_R_ERR_02_auth_*` |
| RUL-34 | Provider degradation. | With Tavily failing (error or 429), with extract failing on both providers, or with Nimble throttled, or with Nimble extract + research **and** Tavily extract + search all refused (Reviewer finding F4; only Nimble search is left), a build still produces exactly the evidence-determined fields: the evidence is defined independently of how the service gathers it (e.g. deep search can replace extract). | §2 "using Nimble alone"; §8 "known exactly when the evidence supports". | `test_R_DEL_03_*` |
| RUL-35 | "Before the first reset the clock follows the system time". | Not testable in a shared run (every test resets); verified by review. | §3.4. | review |
| RUL-36 | Under the F4 faults (Nimble extract + research and Tavily extract + search all refused, only Nimble search answers) is a value that is only reachable through a research claim or an extract of a `searchable: false` page still "evidence" that the field must be `known` for? (Implementer's question) | **Literally yes, practically no: the band does not require it.** §4 defines evidence independent of what a build manages to obtain, but rule 1 of §1 only lets a service assert what a provider served to it, and a non-searchable page is returned by no search, so with research and extract both refused there is no served excerpt to cite. The requirement in §8 (`known` exactly when the evidence supports a value) is therefore read as ranging over evidence **obtainable through the calls that answer**. Hence: (a) such fields are `unknown` and the build is `ready`, not `failed` (Nimble search still succeeded); (b) the F4 test excludes orrin-bay (all its ceo/headcount evidence sits on non-searchable pages) and expects the other companies, whose evidence is all searchable, to be fully `known`; (c) when only *one* of extract/research is refused, or a refusal is transient (429/throttle), the expectation is unchanged (`test_R_DEL_03_*`). A service must not drop supportable fields merely because some searches or pages need more queries than the domain query returns (fenwick-orchards: 12 pages, facts beyond the top 10). | §1 rule 1 (cite only what was served); §4 Evidence; §8 "known exactly when the evidence supports"; §9 budget. Choosing the reading that makes the spec satisfiable. | `test_R_EVD_11_*` |
